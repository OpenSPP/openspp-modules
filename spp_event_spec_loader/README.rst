OpenSPP Event Spec Loader
==========================

This module dynamically generates event data types and all required components (models, views, wizards, security) from YAML program specifications. It enables rapid deployment of event tracking infrastructure for social protection programs without manual coding.

Purpose
-------

The ``spp_event_spec_loader`` module bridges program specifications with the OpenSPP event tracking framework by:

- **Parsing YAML Specifications**: Reads structured program specifications in YAML format
- **Extracting Event Types**: Automatically identifies event types from external systems, compliance conditions, and custom definitions
- **Dynamic Model Generation**: Creates Odoo models for each event type with appropriate fields
- **Automated View Creation**: Generates tree and form views for event management
- **Seamless Integration**: Integrates generated event types with the base ``spp_event_data`` framework

This module dramatically reduces the time and effort required to implement event tracking for new programs or program modifications.

Module Dependencies and Integration
------------------------------------

1. **spp_event_data**: Core dependency providing the base event tracking framework
2. **spp_base_common**: Common OpenSPP utilities and security groups
3. **base**: Standard Odoo base module
4. **pyyaml**: External Python dependency for YAML parsing

Key Features
------------

Program Specification Management
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **YAML Editor**: Built-in YAML editor with syntax highlighting
- **Validation**: Syntax validation and structural verification
- **Metadata Extraction**: Automatic extraction of program metadata (objectives, agencies, languages, currency)
- **State Management**: Draft → Validated → Deployed workflow with error handling

Event Type Extraction
~~~~~~~~~~~~~~~~~~~~~

The module automatically extracts event types from three sources:

1. **External Systems**:
   - Parses ``external_systems`` section in YAML
   - Creates event types for each evidence provider (e.g., DepEd attendance, DOH health compliance)
   - Extracts field definitions from data contracts

2. **Compliance Conditions**:
   - Parses ``compliance.conditions`` section
   - Creates verification event types for each condition
   - Adds standard fields: verified_by, verification_date, result, notes

3. **Custom Event Types**:
   - Supports custom ``event_types`` section in YAML
   - Allows complete control over event type definition

Dynamic Model Generation
~~~~~~~~~~~~~~~~~~~~~~~~

- **Automatic Model Creation**: Creates ``ir.model`` records for each event type
- **Field Management**: Dynamically adds fields based on YAML specifications
- **Type Mapping**: Maps YAML field types to Odoo field types (string→char, number→float, etc.)
- **Standard Fields**: Automatically includes name, summary, description fields

View and UI Generation
~~~~~~~~~~~~~~~~~~~~~~

- **Tree Views**: Auto-generated list views with key fields
- **Form Views**: Auto-generated form views with organized field layout
- **Action Definitions**: Creates window actions for each event type
- **Menu Integration**: Ready for menu integration (requires module extension)

Example YAML Structure
----------------------

.. code-block:: yaml

    program:
      name: "Pantawid Pamilyang Pilipino Program (4Ps)"
      currency: "PHP"
      localization:
        languages: ["fil", "en"]
      implementing_agencies: ["DSWD", "DepEd", "DOH"]
    
    external_systems:
      - id: "DepEd"
        role: "evidence_provider"
        domain: "education"
        data_contract:
          record_type: "attendance"
          required_fields:
            - name: "attendance_pct"
              type: "number"
            - name: "period"
              type: "string"
    
    compliance:
      conditions:
        - id: "edu_attendance"
          description: "Child has ≥85% attendance"
        - id: "health_comp"
          description: "Health package completed"
    
    event_types:
      - id: "house_visit"
        name: "House Visit"
        model: "spp.event.house.visit"
        description: "Field assessment of household"
        fields:
          - name: "is_farm"
            label: "Is Farm"
            field_type: "boolean"
          - name: "farm_size_acre"
            label: "Farm Size (acres)"
            field_type: "float"

This YAML would generate:
- ``spp.event.education.attendance`` model with attendance_pct and period fields
- ``spp.event.compliance.edu_attendance`` model for verification tracking
- ``spp.event.compliance.health_comp`` model for health verification
- ``spp.event.house.visit`` model with farm-related fields

Usage Workflow
--------------

1. **Create Program Specification**:
   
   - Navigate to: Registry → Configuration → Event Spec Loader → Program Specifications
   - Create new record
   - Upload YAML file via "Upload YAML" tab OR manually enter in "YAML Specification" tab
   - Click "Validate" button

2. **Review Extracted Metadata**:
   
   - Check "Program Metadata" tab
   - Verify parsed data in "Parsed Data" tab
   - Review any errors in "Errors" tab

3. **Deploy Event Types**:
   
   - Click "Deploy Event Types" button
   - System creates all models, views, and required infrastructure
   - View created event types via smart button

4. **Manage Event Types**:
   
   - Navigate to: Registry → Configuration → Event Spec Loader → Event Type Definitions
   - View all generated event types
   - Deploy/undeploy individual event types
   - Inspect field definitions and deployment status

5. **Use Generated Event Types**:
   
   - Event types are automatically available in the event creation wizard
   - Create events for registrants using the new types
   - Track event history on registrant forms

Technical Notes
---------------

Dynamic Model Creation
~~~~~~~~~~~~~~~~~~~~~~

The module uses Odoo's ``ir.model`` and ``ir.model.fields`` infrastructure to create models at runtime. Fields are prefixed with ``x_`` to indicate custom/dynamic fields.

Field Type Mapping
~~~~~~~~~~~~~~~~~~

YAML types are mapped to Odoo field types:

- ``string`` → ``char``
- ``number`` → ``float``
- ``boolean`` → ``boolean``
- ``date`` → ``date``
- ``datetime`` → ``datetime``

Deployment Persistence
~~~~~~~~~~~~~~~~~~~~~~

Once deployed:

- Models persist in the database
- Views can be regenerated
- Data is preserved during undeploy operations
- Full cleanup requires manual model deletion

Limitations and Considerations
------------------------------

1. **Module Restart**: Some features (wizard selection updates) require module restart
2. **Dynamic Field Limits**: Complex field types (Many2one, One2many) require manual definition
3. **View Customization**: Generated views are basic; custom views may be needed for production
4. **Performance**: Large numbers of dynamic models may impact system performance
5. **Data Preservation**: Undeploying removes views but preserves model data

Configuration
-------------

External Dependencies
~~~~~~~~~~~~~~~~~~~~~

Install PyYAML:

.. code-block:: bash

    pip install pyyaml

Security Groups
~~~~~~~~~~~~~~~

Access is controlled via OpenSPP security groups:

- **Admin**: Full access to create, deploy, and manage specifications
- **Registrar**: Read-only access to specifications and event types
- **Registry Users**: Read access for created event type data

Templates
---------

The module includes two YAML templates to help you get started:

1. **program_spec_simple_template.yaml** - Minimal template for quick start
2. **program_spec_template.yaml** - Complete template with all available options

Copy either template, modify it for your needs, and upload via the module interface.

Best Practices
--------------

1. **Start with Templates**: Use the provided templates as a starting point
2. **Validation First**: Always validate YAML before deployment
2. **Incremental Deployment**: Test with small specifications before full deployment
3. **Version Control**: Keep YAML specifications in version control
4. **Documentation**: Document custom event types in YAML comments
5. **Testing**: Test generated event types with sample data before production use
6. **Backup**: Backup database before major deployments
